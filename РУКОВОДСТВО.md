# Руководство по использованию tg-userbot

CLI-инструмент на Telethon для **личного аккаунта** Telegram:
сбор никнеймов участников групп → автоматический список рассылки →
отправка сообщений в группы (`broadcast`) и в личные сообщения (`dmsend`).

---

## 1. Установка и запуск

**Требования:** Windows, Python 3.10+ (на этой машине уже готово).

Один раз:
```bat
cd %USERPROFILE%\tg-userbot
py -3.14 -m venv .venv
.venv\Scripts\pip install telethon
copy .env.example .env
:: вписать API_ID / API_HASH из my.telegram.org → API development tools
```

Дальше любая команда запускается так:
```bat
.venv\Scripts\python.exe bot.py <команда> [флаги]
```

Файлы:
| Файл | Что хранит |
|---|---|
| `bot.py` | весь инструмент |
| `.env` | API_ID / API_HASH (секрет, не выкладывать) |
| `userbot.session` | авторизованная сессия аккаунта (не передавать другим!) |
| `userbot.db` | база SQLite: группы, участники, кампании, журнал отправок |
| `exports\*.csv` | выгрузки (UTF-8 BOM, открываются в Excel) |

Переопределение путей без правки кода — переменные окружения
`USERBOT_DB` и `USERBOT_SESSION`.

### Авторизация
```bat
.venv\Scripts\python.exe bot.py login [--phone +420XXXXXXX]
```
Ввести номер → код ( придёт в другие сессии Telegram или в SMS ) →
облачный пароль, если включён 2FA. Результат — `userbot.session`;
пока файл жив, повторный login не нужен.
Уже авторизовано на этой машине: сессия `userbot.session` жива (аккаунт и id —
вне git; посмотреть: `bot.py status`).

## 2. Команды: полный справочник

### `groups` — список рассылки
```
bot.py groups --sync   перебрать все диалоги и добавить все группы/каналы в список
bot.py groups --list   показать список (id, имя, @юзернейм, тип, дата добавления)
bot.py groups --probe  проверить ПРАВА ЗАПИСИ во всех группах аккаунта:
                       каналы-подписки без админства и чаты с закрытым постингом
                       автоматически снимаются с рассылки (in_broadcast=0);
                       права пишутся в покрытие (account_groups.can_write).
                       --keep — только показать, ничего не менять
```
Probe запускай для КАЖДОГО аккаунта (`🧹 Probe всем` в панели): право «писать»
уникально для аккаунта×группа; дирижёр выбирает тот аккаунт, у которого есть
право, и группу, которую не закрыли все.

### `privacy` — броня аккаунтов
```
bot.py privacy --account main [--all]
```
Ставит «Nobody» по максимуму, что позволяет API: номер телефона, last seen, фото
профиля, **ссылка на аккаунт при пересылке** (твои сообщения пересылают —
админы групп и получатели не увидят кликабельный профиль), добавление в чаты,
звонки, P2P (свет IP при звонках), голосовые; «добавление в контакты по
номеру» — единственный ключ с выбором: ставится AllowContacts (минимум для
этого ключа). После каждой записи — обратное чтение с галочкой ✓.
Побочный эффект Telegram: со скрытым last seen ты тоже не видишь точное
время захода других. Запускай сразу после `login` для новых аккаунтов
(`🔒 Приватность всем` в панели).

### `watch` — авто-добавление в реальном времени
```
bot.py watch [--noreply]
```
Дежурит, пока запущен. Что делает:
* первое входящее сообщение из новой группы → группа сама добавляется в список;
* ответ «стоп / stop / opt out / unsubscribe / отпишись» в **личные** сообщения →
  автор заносится в blacklist и получает «Добавил вас в чёрный список, больше не пишу.»
  (`--noreply` — молча заносить без ответа).
Остановка: `Ctrl+C`.

### `scrape` — сбор никнеймов
```
bot.py scrape [--groups 123 456 ...]
```
По умолчанию — все группы из списка рассылки. Каждый участник
(`user_id`, `@username`, имя, флаг бота) сохраняется с привязкой к группе-источнику
(один человек из нескольких групп хранится одной строкой). Повторный запуск
докачивает новых — старые строки не плодятся.
* FloodWait — ждёт указанное сервером время и продолжает; если навязанная
  пауза >10 минут — запуск прерывается с сохранением уже собранного
  (повтори `scrape` позже — он докачает новых, дублей не будет);
* «список участников закрыт для не-админов» (`ChatAdminRequiredError`) —
  Telegram разрешает полный список только админам канала; скрипт пропускает такую
  группу и идёт дальше.
Текущий результат: **18 877 участников** из 29 групп (14 групп с закрытым списком пропущены).

### `broadcast` — рассылка в сами группы
```
bot.py broadcast --text "Привет!" [--file msg.txt]
               [--ids 123 456] [--delay-min 3 --delay-max 8]
               [--max-runs N] [--dry-run]
```
* `--text` или одно из: `--file` — текст из файла;
* `--ids` — выбрать конкретные группы (по умолчанию все активные);
* `--dry-run` — показать получателей, ничего не отправляя;
* `--max-runs N` — отправить максимум N сообщений за запуск;
* пауза 3–8 с между группами; FloodWait — подождать и повторить;
* запрет поста (`ChatWriteForbiddenError` — чужие каналы) пишется как
  `fail:...` в журнал `sent` и не роняет рассылку.

### `dmsend` — личные сообщения собранным участникам
```
bot.py dmsend [--group 1095788921] [--limit 20] [--repeat-ok]
            [--delay-min 20 --delay-max 45] [--max-runs N] [--dry-run]
```
Отбор получателей: есть `@username`, не бот, не в blacklist; по умолчанию
**исключаются те, кому уже успешно писали в прошлых DM-кампаниях**
(`--repeat-ok` разрешает повторно). `--group <id>` — только участники одной группы.
Пауза 20–45 с случайная. Каждый запуск — отдельная «кампания» (видно в `status`).

### `export` — выгрузка в CSV
```
bot.py export [--dir exports]
```
`members.csv` (ник, имя, id, флаги, из каких групп), `groups.csv`, `blacklist.csv`.

### `status` — сводка
```
bot.py status
```
Число групп/участников/blacklist, статистика ok/fail по последним кампаниям,
сколько людей доступно для **новых** DM.

### `blacklist`
```
bot.py blacklist add <user_id | @ник> [--reason "текст"]
bot.py blacklist list
```
@ник ищется в собранной базе (после `scrape`) и заносится с реальным user_id;
если ника нет в базе — команда честно отказывает, а не записывает пустышку.

### `media` — медиа-библиотека поверх «Избранного»
Любое медиа для рассылок живёт в двух местах одновременно: **в «Избранном»
Telegram** (вечное облачное хранилище, доступно с любого устройства аккаунта)
и **в локальном кэше** `media_cache/` (откуда физически отправляет).
```bat
:: загрузить файл: уходит в Избранное аккаунта + копируется в кэш + в реестр
.venv\Scripts\python.exe bot.py media add "%USERPROFILE%\Videos\promo.mp4" --account main
:: подтянуть уже лежащие в Избранном фото/видео (последние 30 сообщений)
.venv\Scripts\python.exe bot.py media pull --account main --limit 30
:: список (id, тип, размер, есть ли кэш)
.venv\Scripts\python.exe bot.py media list
:: если кэш снесён, а в Избранном живёт — вернуть файл:
.venv\Scripts\python.exe bot.py media sync <id> --account main
.venv\Scripts\python.exe bot.py media del <id>   :: убрать из реестра (файл-кэш останется)
```
Прикрепление к рассылке — `--media <id>`, текст становится подписью (caption):
```bat
.venv\Scripts\python.exe bot.py broadcast --media 3 --account main --dry-run
.venv\Scripts\python.exe bot.py conduct --what dm --text "см. промо" --media 3 --limit 5
```
Без текста с `--media` тоже можно — пустая подпись валидна.
В веб-панели для этого карточка **«🖼 Медиа-библиотека»**: кнопка «⬆ Загрузить
файл(ы)» (из любого места диска → тот же `media add`), сетка плиток с превью,
полноэкранный плеер видео (стриминг с перемоткой — Range), кнопки
Pull / sync / удалить, и селектор «медиа» в каждой форме рассылки.

### ☁ `cloud` — облачное зеркало (Supabase)
Опционально: агрегатная статистика оркестра (аккаунты, группы и их права,
кампании и журнал статусов, blacklist, счётчики) синхронится в Supabase —
наблюдение с любого устройства + облачный бэкап. **Собранные ники людей в
облако не уходят** — зеркалит только агрегаты.
1. Создай проект на supabase.com → в **SQL Editor** выполни `supabase/schema.sql`
   (создаст таблицы `tb_*`, RLS-политики: service пишет всё, anon только читает,
   и подключит Realtime).
2. В `.env`: `SUPABASE_URL=https://<ref>.supabase.co`, `SUPABASE_SECRET_KEY=sb_secret_...`
   (секретный ключ — только в `.env`, он в `.gitignore`).
3. Команды:
```bat
.venv\Scripts\python.exe bot.py cloud test   :: связь и наличие схемы
.venv\Scripts\python.exe bot.py cloud push   :: обновить зеркало
.venv\Scripts\python.exe bot.py cloud status :: строки облако vs локально
```
`AUTO_CLOUD=1` в `.env` — push автоматически после broadcast/dmsend/conduct/
scrape/probe/privacy/align/accounts/media/blacklist/export. В веб-панели —
кнопка «☁ зеркало» и чип статуса в шапке. С любого другого устройства данные
видны через Table editor Supabase или подписку Realtime на `tb_*`.

#### 🌐 Vercel-дашборд зеркала (`dashboard/`)
Сам userbot на Vercel не работает (нужен постоянный процесс Telethon, сессии и
пишущая SQLite — serverless для этого не годится). На Vercel живёт **дашборд
наблюдения** поверх облачного зеркала: Next.js, страница + серверный роут
`/api/data` (секретный ключ Supabase только в env Vercel, в браузер не попадает).
- Доступ: открыть URL дашборда → ввести `DASH_TOKEN` (лежит в `.env`).
- Обновление: авто каждые 15 с; при `AUTO_CLOUD=1` данные всегда свежие после команд.
- Повторный деплой: `cd dashboard && vercel deploy -y` (прод: `--prod`).
- Env на Vercel: `SUPABASE_URL`, `SUPABASE_SECRET_KEY`, `DASH_TOKEN`
  (`echo значение | vercel env add ИМЯ production`).

## 3. Мультиаккаунт: единый организм

Все аккаунты работают поверх **одной SQLite-базы** — цели, журнал отправок,
blacklist и cooldowns общие, поэтому аккаунты «понимают» друг друга без
дополнительной синхронизации.

### Подключение аккаунтов
```
bot.py login --account work2            # интерактивный: телефон + код (+ 2FA) в терминале
bot.py accounts import work3 C:\пути\chужой.session   # готовая Telethon-сессия (копируется в sessions/)
bot.py accounts list / enable / disable / remove work3 [--purge]
bot.py accounts budget work2 40         # дневной лимит DM на аккаунт (0 = без лимита — не надо)
bot.py accounts secret work2            # спрятанный ввод api_id/api_hash СВОЕГО приложения
                                        # (иначе наследует .env; можно и env API_ID_WORK2 / API_HASH_WORK2)
```
Правила природы: один аккаунт = один session-файл = один процесс за раз
(Telethon блокирует базу иначе); импорт делает копию файла; повторный импорт
того же файла отклоняется.

### Общее состояние (как у людей в одном организме)
- **Кросс-дедуп DM**: кому успешно писал *любой* аккаунт — никто не повторит
  (`--repeat-ok` отключает).
- **Кросс-дедуп broadcast**: в группу, куда любой аккаунт писал <24 ч назад,
  остальные не дублируют.
- **Общий blacklist**: «СТОП» в DM любому аккаунту (с `watch`) отключает человека
  для всех.
- **Покрытие** (`account_groups`): sync каждого аккаунта помечает, в каких группах
  он состоит; broadcast пишет группу только тем аккаунтом, который в ней состоит;
  чип «покрытие N/M» в панели показывает, все ли группы кому-то доступны.
  Добавил группу одним аккаунтом — она в общей базе и доступна всем, кто в ней
  состоит; чтобы группа стала видима остальным — их `groups --sync` (или `🎭 Синк всем`).
- **Cooldown-реестр**: FloodWait любого аккаунта пишется ему в `flood_until`;
  веб-панель не даст поставить ему задачу (423), а `conduct` просто обойдёт его.

### Дирижёр (conduct) — главный оркестратор
Одна команда, все включённые аккаунты, один общий пул целей:
```
bot.py conduct --what broadcast --text "…" [--ids …] [--repeat-ok] [--dry-run]
bot.py conduct --what dm        --text "…" [--group G] [--limit N] [--accounts work2 main] [--dry-run]
        [--delay-min 20 --delay-max 45] [--window 6]   # окно — максимум часов кампания крутится
```
Алгоритм: аккаунты — параллельные «игроки»; каждый берёт цель из общего пула со
своей скоростью (рандом-пауза). У аккаунта кончился дневной DM-бюджет — он
«уходит отдыхать», цели уходят другим. Прилетел FloodWait — аккаунт ставит себе
паузу в реестр и **возвращает цель в пул немедленно**, её подхватывает свободный.
Серверная цель: суммарный темп = сумма безопасных темпов аккаунтов, а не риск×N.

Пример расчета: 3 аккаунта × бюджет 30 DM/день = до 90 новых диалогов в сутки
без превышения «разогрева» на каждом. Свежий аккаунт: первые 2–3 недели
20–30/день, затем 50–80; зрелый — до ~100 (см. источники в README).

`--dry-run` рисует план раскладки (какая цель какому аккаунту) без отправки;
в панели кнопка «🎼 Запустить дирижёра» (тип dm/broadcast) и живой статус в чипе.

### Веб-панель
- Колонка «покрытие» в таблице аккаунтов + чип «покрытие N/M» и «дирижёр …» в шапке.
- `🎭 Синк/Scrape/Watch всем` — fanout: одна задача на каждый включённый аккаунт
  (по слоту на аккаунт, параллельно).
- Стоп теперь адресный: по аккаунту, по дирижёру, «⏹ всем».

## 4. Типовые сценарии

**Полный цикл (выполнено на этой машине):**
```
groups --sync → scrape → export → broadcast/dmsend
```

**Разведка перед реальной отправкой (ничего не отправляет):**
```
bot.py broadcast --file msg.txt --dry-run
bot.py dmsend --group 1508827399 --limit 20 --dry-run
```

**Малый безопасный пилот DM:**
```
bot.py dmsend --group 1475653688 --limit 10
:: посмотреть reaction-ответы; ответившим «стоп» watch добавит в blacklist
```

**Только что вступил в новую группу и хочу её в рассылке:** либо запустить
`watch`, либо разово `groups --sync` (добавит все новые диалоги).

## 5. База данных (SQLite)

Таблицы: `groups` (список рассылки), `members` (собранные ники),
`member_sources` (user↔группа), `blacklist`, `campaigns` (каждая отправка = кампания,
с авторством `account`: имя или `conductor`),
`sent` (журнал: получатель, ok/fail:ТипОшибки, `account`),
`accounts` (реестр оркестра: session, api_id/api_hash, enabled, daily_budget,
flood_until, user_id),
`account_groups` (покрытие: аккаунт↔группа, кто где состоит).

Свой запрос к базе, например:
```bat
.venv\Scripts\python.exe -c "import sqlite3; print(sqlite3.connect(r'%USERPROFILE%\tg-userbot\userbot.db').execute('SELECT title,(SELECT COUNT(*) FROM members m JOIN member_sources s ON s.user_id=m.user_id AND s.group_id=g.id) FROM groups g ORDER BY 2 DESC LIMIT 10').fetchall())"
```

## 6. Ограничения Telegram — читать обязательно

1. **Полный список участников** доступен только админам канала; чужие
   новостные каналы scrape не соберёт (и broadcast туда не напишет).
2. **Массовые DM незнакомцам — спам.** Telegram банит за них аккаунт
   (ripples → ограничение на чужие DM → бан). Даже при паузах 20–45 с
   18 862 адресата = 5–10 суток непрерывной отправки и высокий риск.
   Разумно: точечно, ≤ 20–30 новых людей в сутки, релевантный текст,
   возможность отписаться (слово «СТОП» + `watch`).
3. **FloodWait** — жёсткие лимиты Telegram; скрипт соблюдает паузы сервера
   автоматически. Не ускоряй `--delay-*` в ущерб сессии.
4. Не держи две авторизации одной сессией одновременно (файл блокируется).

## 7. Веб-панель управления + живой лог (`web.py`)

```bat
.venv\Scripts\python.exe web.py
:: открыть http://127.0.0.1:8642   (другой порт: set WEBBOT_PORT=...)
```

Что умеет:
* чипы статуса (группы, участники, доступно для новых DM, blacklist, текущая задача);
* кнопки быстрых действий: синк групп, scrape (все/выделенные в таблице), export,
  status, `watch` дежурит до нажатия «Остановить»;
* формы **broadcast** и **dmsend** (текст обязателен даже для dry-run, паузы,
  лимиты, группа/повторы) — по умолчанию включён dry-run, ничего не отправляет;
* таблица всех групп с числом собранных участников, последние кампании ok/fail;
* живой лог (SSE): каждая строка stdout задачи летит в браузер мгновенно,
  буфер догоняется при переподключении (при перезапуске сервера клиент сам
  сбрасывает счётчик событий — «boot»-токен), вся история пишется в `logs\web.log`.

Правила: сервер слушает только 127.0.0.1; одновременно идёт **одна** задача
(общая сессия Telethon) — слот резервируется атомарно, второй запрос получает
«занято»; «⏹ Остановить» убивает процесс bot.py (taskkill /T), даже если он
ещё не успел стартовать (отложенный стоп). Кнопки broadcast/dmsend без dry-run
пишут в Telegram по-настоящему — сначала разведка `--dry-run`.

## 8. Траблшутинг

| Симптом | Причина / решение |
|---|---|
| `ModuleNotFoundError: telethon` | запускай `.venv\Scripts\python.exe`, а не системный `python` |
