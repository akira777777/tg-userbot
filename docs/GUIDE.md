# Руководство оператора

Снимок сверки: 9 ноября 2026, каталог `C:\Users\novra\Desktop\tg-userbot`, Windows, PowerShell. Цифры ниже сняты с локальной `userbot.db` в этот день и изменятся после следующего сбора или рассылки.

## Что это

Рабочий продукт — userbot на Telethon: личный аккаунт собирает участников групп в SQLite и по команде пишет в группы или в личку. Точки входа:

- CLI: `bot.py`
- локальная панель: `web.py` (в этой сессии уже слушает http://127.0.0.1:8642 — процесс не останавливать)
- контрольная плоскость Mini App: пакет `control/` и Next.js-приложение `dashboard/`

Интерпретатор на этой машине: `.venv\Scripts\python.exe` (Python 3.14). Зависимости ставить в этот venv, а не в системный Python.

`Makefile` и `docker-compose.yml` описывают другой стек: `fastapi` / `gunicorn` / `uvicorn` и модуль `src.tg_userbot.main:app`. Такого модуля в репозитории нет. Эти цели запускать не нужно — они не поднимут userbot и могут увести в сторону. Рабочий контейнерный вход, если он вообще понадобится, уже описан в `Dockerfile`: `worker`, `controller`, `web`, `healthcheck` и `bot` (дальше аргументы `bot.py`). Повседневная работа идёт с хоста через `.venv`, без Docker.

## Запуск на этой машине

```powershell
cd C:\Users\novra\Desktop\tg-userbot
.\.venv\Scripts\python.exe bot.py status
.\.venv\Scripts\python.exe web.py
```

Панель пишет в лог адрес, на котором поднялась. Порт по умолчанию — `8642` (`WEBBOT_PORT`). Хост по умолчанию в коде — `WEBBOT_HOST`, и если переменная не задана, это `0.0.0.0`, не петля. Проверять состояние: `GET /` и `GET /api/state`. Оба отвечали 200 до правок этого прохода.

Правка фильтра DM попадает в уже запущенную панель только после её перезапуска. Этот проход процесс не трогал: счётчик `dm_available` в живом `/api/state` останется старым, пока панель не перезапустят отдельно. CLI читает код с диска при каждом запуске.

Команды `status`, `export`, `blacklist` и `accounts` работают с базой и не ходят в Telegram. `cloud status` и `cloud test` ходят в Supabase — это сеть, но не отправка сообщений людям.

## Карта команд

Общий вид: `.\.venv\Scripts\python.exe bot.py <команда>`. У команд с сессией есть `--account` (по умолчанию `main`; второй аккаунт в реестре — `work2`).

| Команда | Что делает | Сеть Telegram |
| --- | --- | --- |
| `login` | Авторизация сессии, сохраняет `.session` | да |
| `groups --sync` / `--list` / `--probe` | Список рассылки и проверка права писать | sync и probe — да, `--list` — нет |
| `watch` | Новые группы сами попадают в список; «стоп» в личке пишет blacklist | да, висит |
| `scrape` | Участники групп → `members` | да |
| `broadcast` | Одно сообщение в группы из списка | да |
| `dmsend` | Личные сообщения очереди DM | да |
| `privacy` | Ужимает приватность аккаунта | да |
| `align` | Догон групп, privacy и probe | да |
| `compare` | Сверка покрытия двух аккаунтов | да |
| `conduct --what dm\|broadcast` | Та же рассылка сразу несколькими аккаунтами | да |
| `media add\|pull\|sync\|del\|list` | Библиотека через «Избранное» | кроме `list` — да |
| `export` | CSV в `exports/` | нет |
| `status` | Сводка по базе | нет |
| `blacklist add\|list` | Чёрный список | нет |
| `accounts list\|enable\|disable\|budget\|import\|remove\|secret` | Реестр аккаунтов | нет |
| `cloud push\|status\|test` | Зеркало Supabase | Supabase, не чаты |

Справка: `.\.venv\Scripts\python.exe bot.py --help`.

## Лимиты DM, которые уже стоят в коде

Массовые личные сообщения незнакомым людям — спам по правилам Telegram. Аккаунт за это режут: FloodWait, потом временный бан, потом постоянный. Инструмент только снижает темп, решение запускать рассылку остаётся на операторе.

- `dmsend` по умолчанию берёт не больше `--limit 20` и паузы 20–45 секунд (случайные).
- Успешный DM из любой прошлой кампании и с любого аккаунта повторно не ставится в очередь. Снять это можно только явным `--repeat-ok`.
- Дневной бюджет считается отдельно на аккаунт (`accounts`, по умолчанию в схеме 30).
- `FloodWait` на одиночной отправке приводит к ожиданию; в `conduct` аккаунт уходит на паузу, а цель забирает другой.
- Ответ «стоп» в режиме `watch` сам пишет человека в `blacklist`.
- Сначала имеет смысл смотреть очередь через `status` и `--dry-run`, а не живую отправку.

`broadcast` по умолчанию пропускает группы, куда уже успешно писали за последние 24 часа (любым аккаунтом), если не передан `--repeat-ok`.

## Как выбирается очередь DM

`dm_targets` (её используют `dmsend` и `conduct --what dm`) берёт строки `members` и отбрасывает:

1. `is_bot = 1` — флаг, который Telethon отдал при сборе;
2. username, который в нижнем регистре заканчивается на `bot` (так устроены ники ботов Telegram);
3. `blacklist`;
4. получателей, у которых в `sent` уже есть успешный DM (`status = ok`, кампания `kind = dm`).

Тот же предикат считает строку «доступных для новых DM» в `bot.py status` и поле `dm_available` в панели. Раньше счётчик смотрел только на флаг `is_bot`, поэтому панель и CLI могли разойтись с фактической отправкой. Теперь источник один: `DM_ELIGIBLE_WHERE` в `bot.py`.

`INSERT OR IGNORE` при повторном scrape не обновлял `is_bot`. Из-за этого бот, один раз записанный как человек, навсегда оставался `is_bot = 0`. `save_member` теперь при нике на `bot` (или при флаге Telethon) дописывает `is_bot = 1` и в новую строку, и в уже существующую. Обратно в ноль флаг сам не сбрасывается.

Пока строку не пересоберёт scrape, флаг у старых записей может остаться 0. На отправку это больше не влияет: отбор идёт и по нику.

### Боты и пустые профили

На снимке базы:

| Показатель | Значение |
| --- | --- |
| Участников | 42838 |
| С флагом `is_bot = 1` | 40 |
| С `is_bot = 0` и ником на `bot` | 4 |
| Доступных для новых DM после фильтра | 42794 (раньше в эту цифру входили и эти 4) |
| Строк без username, имени и фамилии | 2003, все они всё ещё в очереди |
| Групп | 68 |
| Аккаунтов | 2 (`main`, `work2`) |
| Чёрный список | пуст |

Имена людей, в которых просто встречаются буквы `bot`, не выкидываются. `Subbotina` и `Rabota` не заканчиваются на `bot`, поэтому остаются. Отсекается только окончание ника: `…bot` в любом регистре, например `HelperBOT`.

Пустые профили не удалялись и из очереди не прячутся. У части из них Telegram отдаёт id без ника и без имени; это не признак бота. Массовое удаление здесь было бы потерей данных, а не очисткой.

Четыре старые строки можно пометить флагом отдельно, без scrape и без отправки. Этот проход запрос не выполнял:

```sql
UPDATE members
SET is_bot = 1
WHERE is_bot = 0
  AND LOWER(COALESCE(username, '')) LIKE '%bot';
```

Откат той же выборкой: `SET is_bot = 0`. Пока запрос не выполнен, `status` продолжает показывать 40 помеченных ботов, а очередь новых DM — уже 42794.

## Облако и дашборд

`cloud push` зеркалит агрегаты в Supabase (таблицы `tb_*`). `AUTO_CLOUD=1` в `.env` включает авто-push после части команд. Сами значения ключей в этот файл и в чат не копировать.

Дашборд — каталог `dashboard/` (Next.js). В обзоре README указан адрес выкладки на Vercel; вход по имени переменной `DASH_TOKEN` из `.env`. Локальные тесты интерфейса авторизации:

```powershell
npm --prefix dashboard test
```

Конфиг тестов — `dashboard/vitest.config.mts`. Расширение `.mts` нужно, чтобы Vitest грузил файл как ESM. Рядом нет `"type": "module"` в `package.json`, и старый `vitest.config.ts` из-за этого печатал предупреждение.

## Mini App: чего не хватает в `.env`

`.\.venv\Scripts\python.exe -m control.main healthcheck` сейчас завершается с ошибкой: требуется `MINI_APP_URL`. Значения ниже этот проход не придумывал и в `.env` не записывал. Их заполняет оператор.

Обязательны для `control.config.ControlSettings`:

- `MINI_APP_URL` — абсолютный `https://` адрес уже выложенной Mini App;
- `OWNER_TELEGRAM_IDS` — свои числовые id через запятую, без посторонних;
- `BOT_TOKEN` — в `.env` имя уже есть (значение не проверялось и не печаталось).

`CONTROL_SESSION_SECRET` healthcheck сам по себе не требует: если имени нет, код подставляет запасную строку из репозитория. Для живой сессии Mini App её нужно заменить длинным случайным секретом. Не использовать пример из `.env.example` как боевой секрет.

`SUPABASE_URL` в `.env` тоже уже есть. `SUPABASE_SECRET_KEY` нужен облачному зеркалу и очереди; наличие ключа этим проходом не устанавливалось.

Пока три пустых имени не заполнены, не запускать `python -m control.main telegram-bot` и `python -m control.main worker`. Воркер умеет звать `bot.py` и тем самым дойти до живого аккаунта.

`docker-compose.prod.yml` при отсутствии переменных подставляет свои запасные `MINI_APP_URL` и `OWNER_TELEGRAM_IDS`. Это не ваши значения. Перед любым запуском compose их нужно задать явно. Файл в этом проходе не менялся.

## Что не запускать на живом аккаунте

Не запускать, если цель — проверка кода, а не реальная работа в Telegram:

- `login`, `scrape`, `watch`, `broadcast`, `dmsend`, `conduct`, `privacy`, `align`, `compare`;
- `media add`, `media pull`, `media sync` (ходят в «Избранное»);
- `test_api_live.py` и `test_media.py` — бьют в живую панель и могут стартовать задания;
- `make dev`, `make run`, `make test` — цели указывают на несуществующий пакет и каталог `tests/`.

Безопасная перепроверка, которой закрывался этот проход:

```powershell
.\.venv\Scripts\python.exe -m pytest -v
.\.venv\Scripts\python.exe test_orchestra.py
npm --prefix dashboard test
.\.venv\Scripts\python.exe bot.py --help
.\.venv\Scripts\python.exe bot.py status
```

`test_orchestra.py` поднимает временную базу и не пишет в `userbot.db`.

1. **Mini App.** Оператор сам вписывает `MINI_APP_URL`, `OWNER_TELEGRAM_IDS` и `CONTROL_SESSION_SECRET`. Пока `healthcheck` красный, контроллер и воркер не запускать. Значения не выдуманы специально.

6. **Перезапуск панели.** Живой процесс на порту 8642 не перезапускался. Новый `dm_available` появится в `/api/state` после отдельного перезапуска.
