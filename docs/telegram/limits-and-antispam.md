# Лимиты, блокировки и антиспам в Telegram

Исследование под проект `tg-userbot`: что именно возвращает сервер, как две разные
системы Telegram наказывают аккаунт, и какие правила из этого следуют для
`broadcast`, `dmsend`, `conduct`, `scrape` и `align`.

Дата редакции: 2026-11-19. Источники — официальные документы core.telegram.org,
Telegram FAQ, документация Telethon и кодовые базы MTProto-клиентов. Числа в
разделе «Практические бюджеты» — эвристика сообщества, а не официально
опубликованный лимит.

---

## 1. Две независимые системы наказания

Их нельзя смешивать: они идут разными путями, требуют разной реакции и
реагируют на разные нарушения.

| | **Anti-flood** (технический) | **Anti-spam** (содержательный) |
| --- | --- | --- |
| Триггер | слишком много запросов одного метода с теми же параметрами за окно | жалобы получателей и групп, семантика сообщения, поведение аккаунта |
| Ответ сервера | ошибка `420 FLOOD_WAIT_X` (и `FLOOD_PREMIUM_WAIT_X`) | ошибка `403 PEER_FLOOD` и ограничение аккаунта |
| Что именно наказано | вызывающий метод + входные данные | аккаунт в целом |
| Правильная реакция | пауза ровно `seconds` и повтор | не повторять; остановиться, ждать дни/недели |
| Срок | секунды-часы, снимается сам | дни → недели → бессрочно (эскалация) |
| Восстановление очереди | цель остаётся тому же аккаунту | очередь не передаётся другим аккаунтам |
| Проверка состояния | `flood_guard` по `accounts.flood_until` | @SpamBot (неофициальный, но реальный индикатор) |

Официальное описание 420 в `core.telegram.org/api/errors`: «The maximum allowed
number of attempts to invoke the given method with the given input parameters has
been exceeded». То есть flood — это *rate limit по паре (метод, входные данные)*.
`PEER_FLOOD` в официальной базе ошибок отсутствует: это спам-ограничение
аккаунта, а не технический лимит метода.

**Вывод для кода:** `FloodWait` и `PeerFlood` должны путиться по-разному
(разные длительности cooldown, разные правила передачи целей), что уже сделано в
`send_error_class` / `target_disposition`. Расширяется только состав
`SPAM_ERRORS` и политика полураспада.

## 2. Ошибки сервера, которые важны для рассылок

Классификация — по коду сервера, а не только по классу исключения Telethon.

| Код | HTTP | Что значит | Как реагировать |
| --- | --- | --- | --- |
| `FLOOD_WAIT_X` | 420 | пауза X секунд | sleep X (+ случайный jitter), цель не терять |
| `FLOOD_PREMIUM_WAIT_X` | 420 | пауза, снимается Telegram Premium | то же; Premium — не обход, только меньше окно |
| `SLOWMODE_WAIT_X` | 420 | slowmode конкретного чата, а не аккаунта | пропустить чат, аккаунт не наказывать |
| `PEER_FLOOD` | 403 | аккаунт ограничен как спамер | стоп канала 24+ ч, цели не передавать |
| `USER_DEACTIVATED_BAN` | 401/403 | аккаунт забанен | выключить аккаунт, ручная разборка |
| `CHAT_WRITE_FORBIDDEN` | 403 | запрет записи в чат | помечать пару аккаунт×чат как `no_send` |
| `CHAT_ADMIN_REQUIRED` | 403 | нужны права админа | `no_send` |
| `USER_BANNED_IN_CHANNEL` | 403 | мьют в канале/чате | `muted` |
| `CHAT_SEND_PLAIN_FORBIDDEN` | 403 | чат запрещает текст | `no_send` |
| `ALLOW_PAYMENT_REQUIRED_X` | 403 | чат требует оплату за сообщение | `payment` |
| `PEER_ID_INVALID`/`USER_ID_INVALID` | 400 | адрес неверен для этого аккаунта | `no_address` |
| `USER_PRIVACY_RESTRICTED` | 403 | личка закрыта | `privacy` |
| `YOU_BLOCKED_USER` | 403 | сам заблокировал | `you_blocked` |
| `CHAT_FORWARDS_RESTRICTED` | 400 | пересылка запрещена | не пересылать, слать своим текстом |
| `AUTH_KEY_DUPLICATED` | 406 | две параллельные основные сессии | не открывать второй коннект к тому же аккаунту |

Последнее важно для оркестра: **один аккаунт = одна основная MTProto-сессия**.
Параллельные соединения к основному DC с одним auth key сервер считает
дубликатом и инвалидирует сессию. В `tg-userbot` это означает: не запускать
два `conduct`/двух воркеров на одни и те же аккаунты одновременно.
(`FloodPremiumWaitError` официально описан для `upload.getFile`; в Telethon'е
он прилетает и на другие методы, поэтому в коде он уже отнесён к флуду аккаунта.)

## 3. Как устроено спам-ограничение (модель поведения)

Публичной спецификации нет. Устойчивые выводы из официальных FAQ, обучения
Telethon и наблюдаемого поведения:

### 3.1 Ответная реакция важнее текста
`telegram.org/faq_spam` прямо говорит: «for private messages, it really doesn't
matter what you send, as long as the receivers find it unwelcome». Главный
сигнал — **доля жалоб** и блокировок от получателей. Массовая холодная
рассылка по нику из поиска («username search is not a tool for making new
friends») — прямо названный антипаттерн.

### 3.2 Ограниченный аккаунт теряет право писать незнакомцам
Ограничение `PEER_FLOOD` не ломает чат целиком: аккаунт может писать тем, у
кого сохранён контакт, и отвечать тем, кто написал первым. Для рассылки это
означает: после `PEER_FLOOD` доставка возможна только тёплой аудитории.

### 3.3 Прогрев и насыщение
Те же FAQ и Telethon: «use the library only on well-established accounts (and
not an account you just created)». Свежий или «нетронутый» аккаунт, который
сразу пишет незнакомцам, ограничивают почти сразу. Официально упомянуты и
причины вне поведения: «previous owners' activities» и «certain virtual/VOIP
numbers». Прокси и IP не отменяют этого, а в «ограниченных странах» (Telegram
сам называет Иран и Россию) номера чаще уходят в бан.

### 3.4 Эскалация
Правило из FAQ: первый раз — «a few days»; повторные нарушения — дольше; если
продолжать — «forever».

### 3.5 Три уровня ограничения
- **бытовое**: часть незнакомцев не получает сообщения, приватные чаты
  могут урезаться;
- **временное ограничение** (`PEER_FLOOD`, дни-недели);
- **бан** (`USER_DEACTIVATED_BAN`, `USER_DEACTIVATED`): аккаунт снят с
  обслуживания, восстановления из кода нет.

### 3.6 Что не является обходом
- Premium не снимает спам-ограничение — он влияет только на
  `FLOOD_PREMIUM_WAIT` и продуктовые лимиты (`*_limit_premium`).
- `@username`-адресация не безлимитна: одинаковый текст в десятки незнакомых
  чатов — тот же паттерн.
- Переключение на другой аккаунт из оркестра **не спасает**, если та же
  кампания идёт параллельно: агрегация идёт по поведению, а не только по
  аккаунту. Поэтому `PeerFlood` в проекте и держит DM-очередь на том же
  аккаунте вместо перекидывания.

## 4. Антиспам-бот и native antispam в группах

Официально (`core.telegram.org/api/antispam`):

- админ супергруппы с ≥ `telegram_antispam_group_size_min` участников может
  включить aggressive-режим (`channels.toggleAntiSpam`);
- после включения Telegram сам мониторит группу и удаляет спам через
  официального бота (`telegram_antispam_user_id`);
- бот не состоит в группе как участник, но показывается в списке админов;
- ошибочное удаление админ может оспорить
  (`channels.reportAntiSpamFalsePositive`), а в клиенте `channelFull.flags2.1
  (antispam)` показывает состояние.

Практический вывод: **в группах с включённым native antispam** сообщение
может удаляться не сразу, а фильтром. Для `broadcast` это значит:

- повтор на «удалённое фильтром» сообщение — прямой сигнал антиспаму;
- группу, где сообщения стабильно удаляются, лучше снять из рассылки, чем
  увеличивать частоту;
- агрессивный режим включают именно на крупных чатах, где холодная
  реклама даёт больше всего жалоб.

## 5. Rate limits по методам и пагинация

Раздел API-лимитов переехал, но для этого проекта важны не таблицы, а
свойства:

- у каждой пары (**метод, параметры**) свои окна; `messages.sendMessage` в
  новые peer'ы — самое дорогое;
- `messages.getParticipants`/`iter_participants` на больших группах упирается
  в `FLOOD_WAIT` и в ограничения приватности участников (Telethon прямо
  предупреждает, что с 2023 у части групп участников вообще нельзя получить);
- `channels.joinChannel` — самый чувствительный к паттерну метод;
- `account.getAuthorizations` и прочее «служебное» читаются реже, но тоже в
  общем лимите на аккаунт.

Поэтому в `scrape` пауза между группами обязательна, а `FloodWait > 10 мин`
корректно прерывает прогон (`cmd_scrape`).

## 6. Slowmode, лимиты чата и `ALLOW_PAYMENT_REQUIRED`

- `SlowModeWaitError` — лимит **чата**: аккаунт не наказывается, цель просто
  откладывается. В коде это `skip`, без пометки цели мёртвой. Правильно.
- `slowmode_exceeds` отсекает чаты, где slowmode длиннее окна кампании, вместо
  ожидания.
- Чаты с `ALLOW_PAYMENT_REQUIRED` требуют оплаты сообщения: это `payment`,
  цель бесполезна для бесплатной рассылки.
- `CHAT_FORWARDS_RESTRICTED` не мешает своим текстом, но делает бесполезной
  схему «переслать готовое из Saved Messages».

## 7. Практические бюджеты (эвристика, не спецификация)

Публичных официальных чисел нет; всё ниже — диапазоны из практики
мульти-аккаунтных инструментов и вендоров. Они дают порядок величины, а не
гарантию. Проект должен этими числами управлять, а не считать их истиной.

### 7.1 DM незнакомцам, на аккаунт в сутки

| Возраст/состояние аккаунта | Осторожно | Мусор-стиль |
| --- | --- | --- |
| 1-4 недели | 10-20 | 0 |
| 1-3 месяца | 20-40 | ~10-20 |
| 3-6 месяцев и более | 40-60 | 20-30 |
| «Прореживание» (после `PEER_FLOOD`/жалоб) | 0, только тёплые | — |

Текущие дефолты проекта (`daily_budget=30`, `delay 20-45 c`) соответствуют
середине диапазона «1-3 месяца» и **не учитывают возраст аккаунта**. Это
главный разрыв, который стоит закрыть.

### 7.2 Вступления в группы

- свежий аккаунт: не больше 5-10/день, с разбросом по часам;
- прогрев: 3-5 дней простой активности перед первым `joinChannel`;
- `align --limit 10` уже это отражает.

### 7.3 Сообщения в группы

- на чат — 1-2 в сутки максимум;
- дедуп 24 ч в проекте консервативнее, чем нужно по риску, но безопаснее;
- уважай `slowmode`: фактический интервал = max(`delay`, slowmode).

### 7.4 Паузы

- DM: 20-45 с — разумный коридор, но для «холодных» серий лучше 45-90 с на
  свежих аккаунтах;
- добавь суточный профиль: активность в рабочие часы целевой аудитории
  (09:00-21:00 по её часовому поясу), а не ровным потоком круглый день.

## 8. Что считать «эффективностью»

`ok` в таблице `sent` — это **не доставка**. Это подтверждение, что Telegram
принял вызов API. Человек мог не открыть сообщение, не прочитать, проигнорировать
или заблокировать. Оптимизация по `ok` увеличивает счётчик, а не результат.

### Три реальных сигнала

| Сигнал | Что значит | Как получается |
| --- | --- | --- |
| `reply` | человек ответил — доставка доказана | `watch` ловит входящее DM и связывает его с отправкой |
| `blocked` | заблокировал — доказуемо, но минус | `UserIsBlockedError` на следующую попытку или ручная отметка |
| `silent` | принято и тишина — **не** доказательство доставки | всё остальное |

`reply_rate` = replied / accepted, `block_rate` = blocked / accepted — оба
считаются только по реальным отправкам, а не по планам.

### Правило интерпретации

- `reply_rate` близок к нулю при живых аккаунтах → проблема в **тексте или
  аудитории**, а не в объёме. Увеличивать объём в этом состоянии — ускорять
  износ аккаунтов без результата.
- `block_rate` растёт → аудитория/оффер нерелевантны; это главный предиктор
  `PEER_FLOOD`.
- Только когда `reply_rate` стабильно ненулевой, увеличение объёма имеет смысл.

### Как это считается в проекте

- `sent.msg_id` — id отправленного сообщения, пишется при успешной отправке
  (`send_run`, `conduct`, `conduct both`).
- `watch` ловит входящие DM: сначала сопоставляет по `reply_to_msg_id`, затем
  по последней отправке этому человеку за 30 дней; пишет `sent.replied_at`.
- `delivery_report(conn, days=7)` и раздел «доставка за 7 дней» в `status`
  показывают accepted / replied / blocked / silent / fail по каждому виду.
- `campaign_report` и `source_report` (команда `bot.py report`) дают разрез по
  кампаниям и по группам-источникам: какая формулировка и какая аудитория
  дают ответы. `experiment_verdict` превращает это в решение:
  `no_data` / `stop_copy` / `scale_winner` / `mixed`.

### Как ставить первый эксперимент

1. Одна маленькая кампания (20–30 DM), один сегмент, один текст.
2. Параллельно — `watch`: без него ответы и отписки не видны и метрика не наполнится.
3. `bot.py report --min-sample 20`. Пока вердикт `no_data` — объём не имеет смысла.
4. `stop_copy` → менять текст/аудиторию, а не количество.
5. `scale_winner` → масштабировать **именно победившую кампанию**, начиная с
   удвоения выборки, а не всего пула.

Без этого раздела любой рост «effective per account» — это рост счётчика
принятых API-вызовов, а не результата.

## 9. Сигналы, которые стоит мониторить

1. **Доля `PEER_FLOOD`** на аккаунт и за сутки. Один случай — уже аварийный.
2. **Доля жалоб/блокировок** (`UserIsBlocked`, ответ «стоп») относительно
   доставок — главный предиктор.
3. **`FLOOD_WAIT`>0 на отправке** — приближение к спам-лимиту.
4. **`fail` по типам** (`privacy`, `deleted`, `no_address`) — качество базы.
5. **@SpamBot** — ручной, но единственный официальный способ узнать статус.

---

## 10. Правила, которые отсюда следуют

1. На каждый аккаунт — свой бюджет по возрасту, а не одна константа.
2. `PEER_FLOOD` — стоп канала на ≥ 24 ч и эскаланция backoff при повторе.
3. `PEER_FLOOD` никогда не переносит цели на другой аккаунт.
4. `FloodWait` — cooldown ровно на `seconds` (плюс jitter), цель не терять.
5. `SlowMode` — пропуск цели, не cooldown аккаунта.
6. Успешная серия не сбрасывает backoff мгновенно: только после окна
   «чистых» дней.
7. Один аккаунт — одна основная сессия.
8. Отписчики и блокировки — в общий чёрный список всех аккаунтов (`watch`).
9. Содержательное разнообразие: варианты текста, персональные плейсхолдеры,
   релевантность группы-источника.
10. Никогда не «доотправлять» в группу, где сообщение удалил native antispam.

## 11. Режим пересылки и его реальный потолок

Схема «автор вне зоны риска» через пересылку: сообщение живёт в закрытом
канале-источнике, наружу уходит `forward` от расходного аккаунта.

### Что это даёт

- `messages.forwardMessages(..., drop_author=True)` — в чате у сообщения не
  будет заголовка «Forwarded from», визуально его отправил аккаунт-пересыльщик.
- Оригинал лежит в закрытом канале: его можно править/удалять после рассылки,
  а не пересобирать текст у каждой цели.
- Исходный текст не рендерится на стороне аккаунта: нет разницы между
  копиями по персонализации — у соседей байт-в-байт один и тот же оригинал.

### Чего это НЕ даёт (проверено по схеме и FAQ)

1. **Жалоба несёт контекст.** FAQ: «они пересылают эти сообщения нашей команде
   модераторов». Модератор видит, из какого чата пришло сообщение.
2. **Автор оригинала резолвится.** `messageFwdHeader` (layer 225) содержит
   `from_id`, `post_author`, `channel_post`, `saved_from_*`. Скрытие автора в
   клиенте — это UI-приватность, а не модерация.
3. **Правило режется по паттерну, а не по подписи.** Same message в десятках
   групп от разных аккаунтов — это и есть сигнал, независимо от «Forwarded from».
4. **ToS API:** «making actions on behalf of the user without the user's
   knowledge and consent» — пересыльщик действует по программе, это его риск.

Поэтому `--forward-from` — это инструмент **снижения заметности и долговечности
поста**, а не иммунитет. Расходник — тот аккаунт, что нажимает «forward».

### Как это в проекте

```bash
bot.py broadcast --from-source @secret_ads --msg-id 12 --dry-run
bot.py broadcast --from-source @secret_ads --msg-id 12
bot.py dmsend --from-source @secret_ads --msg-id 12 --limit 10
bot.py conduct --what both --from-source @secret_ads --msg-id 12 --window 6
```

В `conduct` и `conduct both` источник резолвится **для каждого аккаунта
отдельно**: закрытый канал виден только его участникам, и у каждой сессии свой
кэш entity. Аккаунт, который не видит источник, выбывает из кампании с
сообщением, а не роняет прогон.

| Флаг | Смысл |
| --- | --- |
| `--from-source` | @канал, id или `t.me/...`: аккаунт обязан быть его участником |
| `--msg-id` | id сообщения (можно несколько — альбом) |
| `--forward-from raw` | по умолчанию: `drop_author=True`, заголовок скрыт |
| `--forward-from self` / `--keep-author` | переслать со своим заголовком |
| `--no-preview` | отключить предпросмотр ссылок в текстовой рассылке |

Пересылка идёт по тем же правилам анти-спама: `sent`/`campaigns` журналируются,
кросс-дедуп и дневные бюджеты действуют, `PEER_FLOOD`/`FloodWait` обрабатываются
`target_disposition` как для обычной отправки, `--dry-run` не трогает сеть.

Ограничение `--no-preview`: Telethon 1.45 не умеет custom webpage preview
(в `send_message` нет параметра `webpage`, `SendMessageRequest` — только
`no_webpage`). Полноценный предпросмотр своей ссылки требует `InputMediaWebPage`
или bot-обхода, поэтому пока честно выключается.
